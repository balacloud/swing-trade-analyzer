# Golden Rules: data-providers

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

22. **IN-MEMORY RATE-LIMITER/CIRCUIT-BREAKER STATE IS PER-PROCESS — SHARE IT OR IT'S NOT REALLY PROTECTING ANYTHING.** The Flask backend and the separate `daily_job.py` paper-trading process each ran their own Python interpreter with their own in-memory `circuit_breaker.py`/`rate_limiter.py` state — the two processes were silently *not* sharing rate-limit budgets or circuit-breaker trip state with each other, so a provider tripped/exhausted in one process looked perfectly healthy to the other. Any cross-process safety mechanism (rate limiting, circuit breaking, dedup, locking) needs storage that outlives a single process — here, a shared SQLite store (`backend/data/provider_state.db`). Multi-process deployments (a web server plus any cron/launchd job that imports the same modules) should be assumed by default, not discovered later. (Day 83, data-source review)

25. **WIDENING A CANDIDATE POOL AGAINST SHARED RATE-LIMITED PROVIDERS NEEDS A MEASURED LIMIT, NOT A GUESSED ONE — AND A DETERMINISTIC SORT TURNS RATE-LIMIT FAILURES INTO A SILENT, PERMANENT DATA GAP.** Widening the automated paper-trading engine's MR universe from a static 54-ticker list to a dynamic TradingView scan (Day 89, to accumulate samples faster) first tried limit=300. A live test tripped TwelveData's rate limiter partway through, opening its circuit breaker, which cascaded to yfinance and Tradier too — ~35% of that run's tickers failed on every provider, not because they lacked a signal. Because the query was sorted by `market_cap_basic` descending, that failure always hit the *same* tail-end tickers — a deterministic, silent gap that would have quietly under-sampled the same names every single day, not a random one that evens out over time. Fixed by measuring the real number that completed cleanly (150) and using that as the limit, rather than guessing a "big enough" number. When scaling any batch-fetch loop against a shared, rate-limited provider chain: (1) test at the target scale before shipping the default, (2) if the candidate order is deterministic, a rate-limit cutoff silently and permanently excludes the same tail every run — either keep the limit under the provider's measured sustainable throughput, or randomize/rotate the order so the excluded set changes day to day. (Day 89, MR universe expansion)

36. **A CIRCUIT BREAKER MUST DISTINGUISH "THIS TICKER HAS NO DATA" FROM "THIS PROVIDER IS UNHEALTHY" — THEY ARE NOT THE SAME FAILURE.** Every one of this project's 6 data providers called `breaker.record_failure()` immediately before raising `DataNotFoundError`/`InsufficientDataError` — the same failure tally used to decide whether to trip the circuit breaker and block all further requests to that provider. A ticker genuinely having no data on a given provider (BRK.A on Tradier, a delisted symbol, an unusual dual-class ticker) says nothing about whether the *provider* is healthy — but 3 such misses in a row (a plausible coincidence during any broad daily scan) tripped the breaker exactly as if the provider were down, blocking every *other*, perfectly-servable ticker in that run for a flat 5-minute cooldown. Found investigating why Tradier "didn't help" during a forward-test run: a direct re-test proved it fully healthy (10/10 known-liquid symbols, all <0.5s) immediately after the tripped cooldown window, confirming the earlier trip was a false signal, not real unhealthiness. Fixed across all 6 providers: only genuine connectivity/timeout/rate-limit/auth failures (`ProviderUnavailableError`, `RateLimitError`, `AuthenticationError`, or an uncaught exception) count toward the breaker; a ticker-specific `DataNotFoundError`/`InsufficientDataError` no longer does. When building any health-tracking mechanism (circuit breaker, retry budget, alerting threshold), separate "this specific request's target doesn't exist/qualify" from "the thing serving requests is broken" — conflating them makes the mechanism fire on noise instead of the signal it was built to catch. (Day 95, provider circuit-breaker fix)

40. **A PER-TICKER LOOP AGAINST THE MULTI-PROVIDER ORCHESTRATOR CAN SILENTLY MIX TIMEZONE CONVENTIONS MID-REQUEST — NORMALIZE AT THE ALIGNMENT BOUNDARY, NOT JUST AT INGEST.** The new `/api/sectors/sub-industry` endpoint (Day 101) calls `get_data_provider().get_ohlcv()` once per ticker, 22 times in a single request (21 proxy ETFs + SPY). The first live run failed silently on 13 of 21 clusters with "0 bars aligned with SPY" — not an error, just an empty intersection. Root cause: calling 22 tickers in a tight loop trips TwelveData's rate limiter partway through (the same mechanism Golden Rule 25 already names), and the orchestrator's per-provider fallback chain means the *same request* can serve some tickers from TwelveData (tz-naive) and others from yfinance (tz-aware, `America/New_York`) once the rate limit forces a fallback — while an already-cached SPY series fetched earlier in the same request stays whatever tz it was cached as. `pandas.DatetimeIndex.intersection()` between a tz-naive and tz-aware index doesn't raise; it just returns zero rows, which reads identically to "no overlapping trading days" instead of "these two indices disagree about timezone." This is the project's own Day 52 lesson (`yfinance tz-aware, TwelveData naive; normalize at boundaries`) recurring in a genuinely new shape: single-ticker call sites that only ever hit one provider per request never surfaced this, because a batch `yf.download()` call (like the existing 11-sector endpoint's) returns one internally-consistent DataFrame, not a per-ticker mix. Any endpoint that loops the orchestrator per-ticker across many tickers in one request — not just ones that already know they might rate-limit — should normalize every series to tz-naive immediately before it's ever aligned against another, not just trust that "the orchestrator already normalizes on ingest" holds for every provider in the fallback chain. (Day 101, Sub-Industry Watch)

46. **A PRICE MISMATCH BETWEEN TWO DATA PROVIDERS MAY BE A REAL CORPORATE ACTION, NOT A DATA BUG — CHECK FOR A SPLIT BEFORE ASSUMING ONE SOURCE IS WRONG.** Re-sourcing the `/watchlist-report` skill's `AI_Leveraged` watchlist (Day 107), two of eight tickers (GDXU, SOXL) showed yfinance prices roughly 4x higher than the same tickers' IBKR-verified last price. The instinct to treat this as "yfinance is broken" or "IBKR is stale" would have been wrong either way — both funds had executed a genuine 3-for-1 forward split on 2026-05-25 (a real, leveraged-ETF-typical NAV reset), and yfinance's historical series simply hadn't been re-adjusted for it while IBKR's had. Confirmed directly, not assumed, by re-fetching with `get_price_history`'s `include_corporate_actions=true` flag, which returned the actual split record (`{"type":"Splits","date":"20260525","value":"3.0"}`) — proof, not inference. **How to apply:** whenever two data providers disagree on a price by a suspiciously clean ratio (2x, 3x, 4x — split-like factors), check for a corporate action (split, reverse split) via the provider's own capability before defaulting to "one of these is wrong" — leveraged/geared products in particular reset via splits often enough that this isn't a rare edge case. (Day 107, watchlist-report re-run)

58. **TAKE A BROKER CONTRACT ID FROM THE USER'S OWN WATCHLIST OR POSITIONS, NEVER BY SEARCHING THE TICKER SYMBOL.** The same symbol can be several different instruments. On Day 120, v1 of the Leveraged ETF Board resolved SOXL and GDXU with IBKR `search_contracts` and got the US Direxion/MicroSectors funds (USD). The user holds the Canadian BetaPro funds with the same tickers (CAD, Cboe Canada/TSX). These track different leverage and different underlyings, and they had different splits. Every number on the board was real data for the wrong fund, and nothing errored. Caught only because the user's watchlist listed different conids. **How to apply:** when a page or analysis covers "the user's" tickers, read the conids from `get_watchlist`, positions, or another source the user already owns. Use symbol search only for tickers the user has never held or listed, and then show the exchange and currency so a mismatch is visible. (Day 120, Leveraged ETF Board v1→v2)

61. **NORMALIZE UNITS PER PROVIDER AT THE FIELD MAP, AND TEST THEM WITH VALUES ON BOTH SIDES OF 1.** The same field arrives in different units from different providers. yfinance reports debt/equity in percent (AAPL ≈154) where Finnhub and FMP give a ratio (1.54), and the orchestrator filled D/E from yfinance whenever Finnhub lacked it, so a healthy company could be flagged as heavily indebted. ROE/ROA converters multiplied by 100 only when `abs(v) < 1`, so a real ROE of 150% (1.5 as a decimal) displayed as "1.5%". Both also skewed `assessFundamental()`. A magnitude guess (`< 1` means decimal) fails exactly at the extremes that matter most. **How to apply:** convert unconditionally, per provider, in `providers/field_maps.py` (one place). Bump the cache schema version so cached wrong-unit values are discarded. Add a unit test with real-world values above and below 1 (`backtest/test_data_units.py`). When a card shows a provider number, show which provider supplied it. (Day 123, Fundamentals card)

65. **AN ERROR CODE IS NOT A MEANING: READ THE PROVIDER'S OWN DOCS AND PROBE IT BEFORE CLASSIFYING IT.** Tradier answers HTTP 400, never 429, for an over-the-limit call (its docs, "Quota Violation"), and ALSO for an unknown ticker on `/markets/history` ("symbol not found") and for a bad date. Our code knew only 429/401/403/5xx, so every 400 fell through to `raise_for_status()` and counted as "Tradier is broken": three unknown tickers in a row could switch Tradier off for 5 minutes (Golden Rule 36 again), while a real quota hit would have looked like any other failure. Two live probes (not the docs alone) also showed the quotes endpoint answers an unknown symbol with HTTP 200 and `unmatched_symbols`, so one rule did not fit both endpoints, and an empty symbol hangs until the timeout. The Opus review added that a 400 we cannot classify is most likely OUR request bug and must fail loudly, never be filed as "no data". **How to apply:** before mapping a provider's status codes to meanings, read its docs for the codes it actually uses, probe each endpoint with a good, an unknown and a malformed request (one call each), and classify on the body text as well as the code. Unknown bodies raise a loud error and stay out of the health counters. Test with fake responses against a throwaway state file. (Day 128, Tradier)

67. **A PROVIDER'S "I DON'T HAVE IT" IS NOT A HEALTH SIGNAL, AND AN ERROR MESSAGE MUST NEVER CARRY THE KEY.** Twelve Data answers HTTP 404 for symbols it does not carry (`.TO`, `.NE`, `^VIX`, `BRK-B`). The provider had no 404 branch, so `raise_for_status()` raised, the generic `except` counted a breaker failure, and the same exception text held the request URL with `apikey=`: 315 false "404 Client Error" failures and 324 log lines with the live key, found only because an Opus review of the Alpaca plan asked what the existing provider did with the same case. This is Golden Rule 36 again, one provider later. **How to apply:** for every provider, list the codes it uses for "not covered" and map them to no-data BEFORE any generic raise; check coverage (`providers/coverage.is_us_symbol`) before spending a limiter token or a call; build error text from the exception TYPE and status, never from the URL, headers or params (`raise ... from None`); grep the log for `apikey=` after any provider change. (Day 129, Twelve Data / Alpaca)
