# Golden Rules: cache-time-audit

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

23. **A BACKGROUNDED DEV SERVER'S STDOUT DIES WITH ITS LAUNCHING TERMINAL — REDIRECT IT.** `start.sh` ran `python backend.py &` (and `npm start &`) with no output redirection, inheriting the launching terminal's stdout/stderr file descriptors. When that terminal window closed, the backend process survived (reparented to launchd/PID 1) but its stdout fd became invalid — every subsequent `print()` call (used throughout the codebase for request-scoped logging, including inside exception handlers) threw `OSError: [Errno 5] Input/output error` and turned into a 500, even for otherwise-healthy requests. The failure was silent on the frontend too: fetch handlers caught the error and set state to `null` with no error banner, so a card just disappeared with no signal it had ever been broken (same failure shape as Golden Rule 6's "never hallucinate/silently swallow" lesson, one layer down the stack). Fix: `nohup <cmd> >> logfile 2>&1 & disown` for any backgrounded long-running process — redirect output to a file and detach it from the controlling terminal so closing the window can't touch its file descriptors. Assume any `&`-backgrounded server will eventually outlive its terminal. (Day 84, backend/frontend reliability fix)

28. **STAMP DATES FROM THE DATA, NOT THE WALL CLOCK — A FORCE-RUN ON A NON-TRADING DAY CAN PERMANENTLY ZOMBIE A SIGNAL.** `paper_trading/daily_job.py` computes `today = datetime.now().strftime('%Y-%m-%d')` and `live_signals.py` stamped every new signal's `signal_date` with that same raw wall-clock value, even though `signal_price` was correctly read from the ticker's actual last OHLCV bar two lines above it. Force-running the job on a weekend (the "Force Run Now" UI button has no day-of-week guard) stamped `signal_date` as a Sunday — a date that can never appear in any OHLCV DataFrame's trading-day index. `activate_pending_signals()`'s `_find_index_for_date()` lookup then failed on that row forever, every single day, with only a `print()` nobody sees (the UI trigger route is synchronous and aggregate-only, per the Day 90 finding) — a silently, permanently stuck `pending_entry` that would never become a real trade. Found by re-running the job in the foreground after a Force Run "looked like nothing happened" and reading the actual stdout. 8 of momentum's 11 pending signals were affected — a meaningful fraction of an already slow-accumulating sample. Fixed by deriving `signal_date` from `stock_df.index[-1]` (the same row `signal_price` already came from) instead of `datetime.now()` — self-consistent by construction, no market-calendar library needed. The 8 already-stuck rows were repaired by matching their stored `signal_price` back to the OHLCV row it actually came from (unique price match within the recent window) and correcting `signal_date` to that row's real date; all but one activated on the next run (the last was correctly still waiting on a stale cache, not stuck). Same family as Rule 27: don't trust "when I ran this" as a proxy for "what the data says happened" — read the data's own timestamp. (Day 92, force-run investigation)

31. **A CACHED RESPONSE CAN OUTLIVE THE FIX THAT WAS SUPPOSED TO CHANGE IT.** Several fixes this session (the Cap Size Rotation wording/color bugs, the econ composite PMI-key bug, the Seasonal Regime text softening) initially appeared not to work when re-checked live — not because the code was wrong, but because `/api/sectors/rotation` (cached per trading day) and `/api/cycles`/`/api/econ` (cached 6h) were still serving the pre-fix response from `data/cache.db`'s `market_cache` table. Each required an explicit `DELETE FROM market_cache WHERE symbol='...'` before the fix became visible. A correct code fix and a stale cache produce the exact same symptom from the outside ("I fixed it and nothing changed") — when verifying a fix against a cached endpoint, invalidate that specific cache key first, or a live check can falsely fail (or, worse, falsely pass by coincidentally matching what the stale cache already happened to show). (Day 92, Sectors/Context tab audit)

33. **A SCHEDULED JOB'S "LOCAL TIME" COMMENT IS A CLAIM ABOUT THE MACHINE, NOT A FACT — VERIFY IT.**
 The paper-trading `launchd` plist's `StartCalendarInterval` fired at Hour=16 with a comment claiming "16:30 Central Time (this machine's local timezone)." A user question ("is it CST or EST") prompted checking `/etc/localtime` directly, which showed the machine's real local timezone is America/Toronto (Eastern) — `launchd` interprets Hour/Minute fields in whatever the OS actually thinks is local time, not whatever a comment assumes. The mismatch silently shrank the intended ~90-minute post-market-close settling buffer (chosen so daily bars had time to settle across the TwelveData/yfinance/Stooq provider chain) down to only ~30 minutes, for an unknown number of sessions, with zero symptom loud enough to surface it — the job kept running and recording trades, just with less buffer than designed. Any time a scheduled job's documented "fires at X in local time" matters for a downstream assumption (data settling, market-hours alignment, rate-limit avoidance), check the actual system timezone (`date`, `/etc/localtime`, `systemsetup -gettimezone`) rather than trusting whatever a prior comment or setup script assumed — the machine may have been reconfigured, or the assumption may simply have been wrong from the start. (Day 95, paper-trading schedule fix)

39. **A LIVE ENGINE THAT REPLAYS HISTORICAL BARS MUST VERIFY THE LAST BAR IS ACTUALLY CLOSED — A PROVIDER WILL HAND YOU A PARTIAL ONE, AND A JOB THAT CAN BE RUN MANUALLY WILL EVENTUALLY BE RUN MID-SESSION.** The automated paper-trading engine was designed and reasoned about, from Day 81 onward, as a strictly once-daily post-close job — every review since assumed that execution context. But `--force` (Day 81) and the "Force Run Now" UI button (Day 88) both quietly broke that assumption: the data provider returns a **partially-formed bar for the current session while the market is still open**, and neither `simulate_trade()` nor `simulate_mr_trade()` checked bar completeness before reading its High/Low/Close — so a mid-session manual run could write an intraday, not-yet-final price into the ledger as that day's closing price, and `close_position()` is one-way, so the error was permanent. Found via a targeted, prophylactic Opus review (Day 99) of the highest-stakes, least-recently-scrutinized code in the project — nothing was visibly broken; the review was chosen specifically *because* nothing looked broken, not in response to a symptom. Exhaustive re-replay (not a spot-check) found 19 of 25 closed MR trades affected, including one (MS) that should still have been an open position. While the fix was mid-implementation, a real Force Run click during market hours reproduced the exact bug live and independently, confirming it wasn't hypothetical. Fixed by stripping the final bar whenever it's dated today and the market (checked via an explicit `zoneinfo` market timezone, never machine-local time — Golden Rule 33's lesson applied again) hasn't closed yet, applied at the single shared OHLCV-normalization chokepoint so every call site was covered by one edit. When building any live/production job meant to replay or step through historical bars, check bar completeness explicitly — don't assume the execution context (post-close only) that was true when the job was first designed will stay true once a manual trigger exists. (Day 99, partial-bar ledger contamination fix)

43. **CLEARING A BACKEND CACHE IS NOT THE SAME AS INVALIDATING FRONTEND STATE THAT ALREADY FETCHED FROM IT.** The Sectors tab's "Refresh Session" button correctly cleared the backend's per-trading-day `market_cache` (Sector Rotation, Sub-Industry Watch, SRPS Pullback Screener) via `POST /api/cache/clear` — but the tab's own `sectorRotation` state (fetched once on mount into `App.jsx`) and its two lazy-loaded sub-sections' local `data` state (fetched once on first expand) had no code path connecting a cache-clear action to a frontend re-fetch. The result: clicking Refresh Session repeatedly showed the exact same numbers, with no error, no stale-data indicator, nothing to suggest anything had changed — a genuinely different failure shape from Golden Rule 31 ("a cached response can outlive the fix," about verifying a fix against a live endpoint) and from Golden Rule 30 (a field never reaching the UI at all) — here the data pipeline was completely correct on both ends, but the *action* that was supposed to connect "user wants fresh data" to "component holding old data" simply didn't exist. Found from a real user report ("looks like this is stale... I don't think it's reflecting proper info, it's not failing loud") — reproduced by checking the actual mount-effect/local-state code, not assumed. Fixed by threading a bump-able `refreshTrigger` prop from the button handler down into every component holding independently-fetched state, each with its own `useEffect` that discards stale data (and refetches if currently visible) when the trigger changes. **How to apply:** any UI action framed as "refresh" or "clear cache" must be audited for every piece of frontend state it's supposed to invalidate, not just the backend cache key — a correct backend-side clear with no corresponding frontend re-fetch path produces the exact same symptom as a caching bug, but needs a completely different fix. (Day 105, Sectors tab staleness fix)

66. **AUDIT THE COPY OF THE DATA THE APP ACTUALLY USES, NOT ONLY A FRESH DOWNLOAD.** The Day 127 data audit fetched each provider fresh and graded it clean, and the live app still sent invalid JSON (`"currentPrice": NaN`) for 15 tickers: Yahoo had given an after-hours history whose newest bar had no prices, the cache stored it, and the cache kept it until the next close. The audit could not see it because it never read the app's saved copy; the Data Sources tab even called that copy "fresh" because "last bar" was taken from the empty row. It was found only because the page checker printed "response body unreadable" while still passing. **How to apply:** an audit of data must read what the app serves (its cache and its responses), not only what a provider would give today. Keep the cache RAW so such checks can see a fault, and clean the data where it is served, once (`market_time.drop_empty_close`). A checker must FAIL on an unreadable answer, never just warn. When a result looks fresh, ask which row it is "fresh" by. (Day 128, empty price row)

68. **AN AUDIT CHECK MUST READ WHAT THE USER SEES, AND A FIXED CACHE RULE MUST COVER EVERY SOURCE.** Audit check C8 graded "Tradier served this" from its own list, while the Data Sources tab said something different (it already warned on some tickers and not on others), so the plan's claim "the tab shows no warning" was wrong and nothing would have caught it. Separately, the 16:00-16:30 cache hole (a frame fetched while the closing bar may be unfinished, kept until the next day) was independent of the source and survived two source changes until the Alpaca review. **How to apply:** an audit check reads the same field the page renders (`/api/provenance` `quality.checks`), and a plan claim about what the page shows is verified on the page, not in code. A cache or expiry rule goes at the one write point (`cache_manager.set_cached_ohlcv`) so every source gets it; test it with a mutation (disable the rule, expect failures). (Day 129)
