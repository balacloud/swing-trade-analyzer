# Golden Rules: display-consumers

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

30. **A NEW BACKEND FIELD ISN'T LIVE UNTIL EVERY INTERMEDIATE TRANSFORM LAYER PASSES IT THROUGH.** Adding `macro_alignment`/`macro_alignment_status` to `/api/sectors/rotation`'s response, then wiring the frontend to read them, produced nothing — no error, just silently absent. The backend was correct; the bug was in `frontend/src/services/api.js`'s `fetchSectorRotation()`, which doesn't pass through the raw JSON but manually reconstructs a whitelisted object literal (`return { sectors: data.sectors, size_rotation: data.size_rotation, ... }`) — any field not explicitly listed is silently dropped. A pure code-read of the backend endpoint would never have caught this; only checking the actual rendered page did (Golden Rule 6). When adding a field to any backend response, grep for every frontend function between the fetch and the component that might reconstruct rather than pass through the object, and confirm the field survives the whole path — don't assume "the backend returns it" means "the UI receives it." (Day 92, Sectors↔Context macro_alignment connection)

38. **WHEN REUSING AN EXISTING FIELD FOR A NEW AXIS OF VARIATION, DOCUMENT BOTH MEANINGS EXPLICITLY — DON'T LET ONE COLUMN SILENTLY MEAN TWO DIFFERENT THINGS.** The `paper_positions` ledger's `variant` column was built Day 95 to mean "which entry-gate experiment" (momentum's Path A flat/ATR proxy vs. Path B's real S&R gate). Building the Day 98 HUB-65 curated-universe MR forward-test track needed a second, orthogonal axis — "which ticker universe," not "which gate" (MR's gate is completely unchanged between the broad scan and HUB-65, only the candidate list differs). Reusing the same `variant` column (`'mr_hub65'`) instead of adding a new `universe` column was the right call — zero schema churn for one curated list — but only *because* it was paired with an explicit schema comment in `ledger.py` stating both meanings by system (`momentum` → gate experiment; `mr` → universe) up front, not left implicit. Without that comment, a future audit reading "variant" in isolation would reasonably assume it always means the same axis across every `system` value, and could misinterpret or mis-filter HUB-65 trades as another gate variant. When a column/field is deliberately reused for a second purpose elsewhere in the schema (cheaper than adding a new one, per Golden Rule 7's DRY principle), the reuse itself isn't the risk — an undocumented second meaning is. Write the "this means X for A, Y for B" comment at the point of reuse, not after someone gets confused. (Day 98, HUB-65 curated-universe MR forward-test)

44. **A BATCH STATUS CHECK THAT CAN FAIL FOR 3+ STRUCTURALLY DIFFERENT REASONS MUST NOT COLLAPSE THEM INTO ONE GLYPH.** The Scan tab's Breakout column rendered a bare `—` for three genuinely different situations: a ticker ranked beyond the batch endpoint's 20-row cap (never requested at all), a ticker that was requested but the batch call failed or returned no result for it, and a ticker that resolved cleanly to the engine's own `NOT_READY` state (checked, nothing special found). All three read identically to the user — indistinguishable from each other and from "this is broken." The backend already distinguished these cases in its response shape (`{error: "..."}` vs a valid `{status: "NOT_READY", ...}`) — the collapse happened only in the frontend's render branch, which treated `b == null`, `b.error != null`, and `b.status === 'NOT_READY'` as one case. Fixed by tracking which tickers were actually included in the last batch request (a `Set`, captured before the request resolves so it survives even a fully-failed call) and giving each of the four distinct outcomes its own honest, still-muted label ("Not checked" / "Unavailable" / "Data error" / the engine's own "Not Ready" badge, reused rather than reinvented). Same family as Golden Rule 36 (a circuit breaker must distinguish "no data for this ticker" from "the provider is unhealthy") one layer up the stack, at the UI instead of the data layer. **How to apply:** whenever a status/badge cell can be empty for more than one reason, enumerate the actual reasons before writing the render branch — "never checked," "checked but no result," "checked and errored," and "checked and genuinely neutral" are four different facts a user might need to act on differently, and a single placeholder glyph can't carry that distinction even when every individual case is, on its own, "nothing urgent." (Day 106, Scan tab breakout-badge labeling fix)

51. **BEFORE REDESIGNING WHAT A DECISION ENGINE DISPLAYS, AUDIT WHICH VIEW IS ACTUALLY THE DEFAULT AND EVERY LIVE CONSUMER OF THE VALUE BEING CHANGED — NOT JUST THE PRIMARY DISPLAY SURFACE.** 13 decisions were locked for redesigning the Analyze page's "Full Analysis" view — its verdict badge, R:R display, position sizing — without checking that `analysisView` actually defaults to `'simple'` (Day 75), meaning the page the user lands on first is the *unredesigned* Simple Checklist, complete with a `text-4xl` hard TRADE/PASS verdict and its own R:R≥2.0/ADX≥20 gates. The redesign as originally scoped would have changed the page one click deeper than the one actually seen first. Separately, the composite verdict being demoted from the page's headline had five live consumers beyond the badge itself (an AVOID-contradiction warning, a suppressed position-size condition, a "why this verdict" panel, a Simple-view comparison strip, and a trade-logging data field) — only the first-order display had been accounted for. Same shape as Golden Rule 32's "what else calls the thing I changed," one layer up: not just does the immediate change work, but which surface does the user actually see first, and what else silently depends on the value being redesigned. **How to apply:** before locking a redesign's scope, grep for every live consumer of the value being changed (not just the one on the screen being discussed) and confirm which view/state is the actual default a user encounters — a redesign that's internally consistent but scoped to the wrong entry point, or that leaves orphaned logic behind, isn't actually done. (Day 109, Analyze Page Redesign)

54. **A FUNCTION THAT LOOKS LIKE PURE DISPLAY SUPPORT CAN ALSO BE SILENTLY LOAD-BEARING FOR A LIVE FORWARD-TEST GATE — CHECK EVERY CALLER BEFORE SCOPING ANY FIX AS LOW-RISK.** After grading `support_resistance.py`'s `_pivot_sr()` 2/10 and writing a concrete, small fix plan for its extreme-vs-nearest bug (Golden Rule 53), the natural next step was to just build it — the fix looked purely additive to the Analyze page. Before any code was written, a direct check of every caller of `compute_sr_levels()` found it isn't Analyze-page display support at all in one real sense: `backend/paper_trading/live_signals.py` imports it directly, and Momentum Path B's live entry gate — a real, running forward-test track, 117 trades deep by the time this session closed — gates real signals on `sr_levels.meta['trade_viability']['viable']` and the R:R computed from those same levels. Fixing the selection logic in place would, per Golden Rule 18, reset Path B's accumulated count to zero. This wasn't caught by the fix plan itself (the fix plan was correct and small) — it was caught by the discipline of tracing every caller of the function being touched, one level removed from the specific bug being fixed, before writing a line of code. **How to apply:** before scoping any fix — however small, however "obviously safe" — as low-risk, display-only, or freeze-independent, grep for every caller of the function/module being touched, not just the ones already in view from the current task. A function can serve two masters (a display page and a live entry gate) without either caller's code suggesting the other exists. This is the same discipline Golden Rule 47 already applies to config drift and Golden Rule 32/41 apply to code review passes, run one level earlier — at scoping time, before implementation starts, not after. (Day 111, S&R fix scoping — caught before any code was written, a genuine save, not a near-miss)

57. **BEFORE ADDING A FIELD TO AN OBJECT, CHECK WHETHER SOMETHING ELSE ENUMERATES THAT OBJECT'S KEYS AS DATA — A NEW KEY CAN BE SILENTLY SWEPT INTO AN UNRELATED COUNT.** Planning the Day 117 absolute-momentum read, the natural-looking design was to add the stock's own 1-year return as a new top-level key on `simplifiedResult.criteria` (the Simple Checklist's 9-criterion object), next to `trend`/`momentum`/`setup`/etc. That object isn't just a bag of display data — three other places treat its *key set itself* as meaningful: `Object.values(criteria).filter(c => c.pass)` computes `passCount`, `.map(c => c.label)` builds the "Close but missing" summary, and `App.jsx` renders one card per `Object.entries(criteria)` key against a hardcoded `totalCriteria: 9`. A tenth key would have silently become a tenth checklist criterion — rendered, counted, no error, "looks like it works" — a direct violation of "informational only" arriving through a change nobody would call a gate. Caught only because the Opus plan traced every consumer of `criteria` (Golden Rule 54's discipline, but aimed at a *data shape* instead of a *function*) before designing the field; the fix was to nest the new value as a sub-field on the existing `momentum` entry instead. Day 118's MTF work independently avoided the same trap the same way — `strength_label`/`proximity` went inside each `confluence_map[level]` value dict, never as new top-level keys next to `confluent`/`weekly_match` that some future `Object.keys()` might enumerate. **How to apply:** before adding any new field to an object, grep for every place that object (or its keys/values) gets enumerated generically — `Object.keys/values/entries`, a `.map()`/`.filter()` over it, a `for...in`, a count derived from its length — and confirm a new key wouldn't be swept into that enumeration's meaning. When in doubt, nest the new field inside an *existing* entry rather than adding a sibling key. (Day 117, absolute-momentum read planning — a genuine save, caught before any code was written)

63. **ONE LABEL, ONE NUMBER: A WORD OR PRICE ON THE PAGE MEANS ONE THING EVERYWHERE.** Fable caught this twice in one day. "Ceiling" meant Trade Setup's nearest resistance in one card and the breakout's 60-day high in another, two different prices for the same stock (RIVN $14.31 vs $17.16). And the first S&R plan would have shown two different Buy prices, because Trade Setup reads `max(support)` while the Simple Checklist reads `suggestedEntry`. A reader who sees the same word twice assumes it is the same number. **How to apply:** before adding a label or a price to a card, grep the page for the same word and for every other place that computes the same quantity. If two numbers differ, give them different names ("Resistance" vs "60-day high"), or make both read one source. Check badges, tooltips, skills and help text too, not only the card body. (Day 125, Analyze cleanup)
