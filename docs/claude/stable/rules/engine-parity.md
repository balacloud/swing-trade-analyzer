# Golden Rules: engine-parity

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

19. **SYSTEMATIC GRID-TEST PARITY, NOT HAND-PICKED VECTORS.** `categorical_engine.py`'s 5 hand-written parity vectors passed for years while a real bug sat undetected: the Python HOLD-fallback was missing a `risk_macro == 'Neutral'` branch that live JS had, silently defaulting to AVOID instead. A systematic 86,400-combo grid (`test_verdict_parity.py`) found it in one run — a 7.08% mismatch rate that 5 spot-checked vectors could never have surfaced by chance. When two independent implementations of the same logic must stay in sync (e.g., a Python backtest port vs the live JS it's meant to validate), build an exhaustive input grid over the decision boundaries, not a handful of "representative" examples. (Day 78, Fable Remediation Task 2.4)

21. **WHEN BUILDING A LIVE COUNTERPART TO AN EXISTING BACKTEST ENGINE, DRY THE SHARED LOGIC BEFORE WRITING THE SECOND IMPLEMENTATION — not after finding a parity bug.** Rule 19 found the JS/Python verdict-parity bug after it had shipped for years. Building the automated paper-trading engine (Day 81) was a chance to apply that lesson proactively: instead of writing a second exit-logic state machine for live positions, `trade_simulator.py`/`mr_simulator.py` gained a `live_mode` parameter so the live engine replays the *exact same* backtested function, and the Config C TradingView query was factored into `scan_queries.py` so the live Scan tab and the paper-trading engine can't drift apart. Verify the extraction is behavior-preserving (byte-for-byte identical output on real/synthetic trades) before relying on it — a refactor that "looks equivalent" is not the same as one that's been diffed against the original. (Day 81, automated paper trading engine)

29. **A LIVE PAPER-TRADING REPLAY MUST READ BACK VALUES ALREADY LOCKED IN AT ENTRY, NOT RECOMPUTE THEM FRESH EVERY DAY.** `daily_job.py`'s `step_open_positions()` called `simulate_trade()`/`simulate_mr_trade()` without passing the `initial_stop_price`/`initial_target_price` the ledger had already stored at entry (`compute_entry_levels()` already existed for exactly this purpose) — so every daily replay silently recomputed stop/target fresh from whatever the current OHLCV window and code produced. This isn't just a hypothetical: verifying the fix caught a live instance of the exact drift risk it prevents — KRYS's freshly-recomputed stop (332.18) had already drifted from its stored entry value (333.37) due to an upstream provider data revision, with zero trace that a drift had occurred. A future edit to the entry-level formula would have the same silent effect on every already-open position. Fix: pass the ledger's stored `initial_stop_price`/`initial_target_price`/`max_hold_days` as overrides into the simulator (the override params already existed, just weren't wired up) — anchor every replay to what was actually decided at entry, not to what today's code/data would decide if asked fresh. Same integrity principle as Rule 21 (DRY the exit logic) one layer deeper: sharing the *function* isn't enough if the *inputs* to that function are allowed to drift. (Day 91, paper-trading exit-rule integrity fix, Session 28 audit)

35. **LIVE/BACKTEST LOGIC PARITY MUST BE VERIFIED DIRECTLY, NOT ASSUMED FROM A SHARED NAME OR COMMENT.** `paper_trading/live_signals.py`'s momentum R:R check has called `backtest/trade_simulator.py`'s `compute_entry_levels()` (flat +8% target, ATR-clamped stop) since Day 81, and its own docstring even claimed this used "the exact same thresholds the backtest uses." It didn't. `backtest_holistic.py`'s actual Config C entry gate (`check_entry_signals()`) computes R:R from real support/resistance levels entirely — `compute_entry_levels()` was only ever the *exit-management* formula in the real backtest, never the entry decision. This went undetected from Day 81 (when the automated engine was built) until Day 95, when a live investigation into a suspiciously high rejection rate led to actually diffing the two code paths against each other — nobody had had a reason to compare them before. Same bug class as Golden Rule 19 (JS/Python verdict parity), one layer over: whenever a live/production path is built to "replay" or "match" a backtest's validated logic, trace the actual call graph and confirm it calls the *same function* the backtest's real decision point uses — a plausible-sounding docstring claim is not verification, and two functions computing "R:R" is not evidence they compute the *same* R:R. Fixed by building Path B, a parallel experiment using the real S&R-based gate, tracked separately so Path A's existing count stays valid. (Day 95, R:R gate investigation)
