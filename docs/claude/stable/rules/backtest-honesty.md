# Golden Rules: backtest-honesty

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

16. **EQUAL WEIGHT — Never optimize category weights.** DeMiguel et al. (2009): equal weights beat optimized out-of-sample. 238 trades is insufficient to optimize 4+ weights. If future evolution moves to continuous scoring, start with equal weights. (Day 69, Tier 1B)

18. **REUSED OOS IS NOT OOS — freeze before forward test.** Every tuning pass that peeks at the same walk-forward window converts out-of-sample into in-sample. Days 55–75 reused the same 2020–2025 split across ~20 tuning sessions, so "OOS outperforms IS" no longer certifies robustness. Before paper/forward testing: pre-register the exact config (all thresholds + success/failure criteria), then never re-tune against the same historical window to "fix" a validation result. (Day 78, Fable review)

20. **A PRE-COMMITTED RESTRICTION IS NOT A RE-TUNE.** Rule 18 forbids re-tuning thresholds to chase a better backtest number — but MR's original entry condition had NO liquidity gate at all (only `price > $5`, unlike momentum's $5M ADV gate). Adding a liquidity floor (price>$10, 20d ADV>$25M) decided *before* seeing the result, for a defensible, principled reason (execution realism — Connors' RSI(2) research was validated on liquid large-caps, not shell/SPAC names), is a legitimate one-time re-test — not data-snooping. It flipped MR from a clean null (PF 0.99) to a real-but-modest result (PF 1.16, still not significant at p=0.064). The distinguishing test: was the change decided *because of* the disappointing number (forbidden), or was it a *quality/execution constraint* that happened to also be untested (legitimate, once)? Either way: run it once, accept the answer, don't iterate further. (Day 79/80, Fable Remediation MR liquidity re-test)

45. **A FIXED RANDOM SEED ONLY REPRODUCES A SAMPLE AS LONG AS THE UNDERLYING DATA SOURCE DOESN'T CHANGE.** Re-running `backtest_survivorship_free.py`'s universe construction (`build_unbiased_universe()`, seed=42, 400-ticker random sample) as part of a Day 106-107 research spike produced a materially different Config C baseline (PF 0.97) than the documented canonical number (PF 1.40, Day 79) — not a code bug (confirmed via `git diff`: the spike's own change was purely additive, zero lines touching Config C's own gating logic), but a real, silent drift: `simfin_loader.get_available_tickers()` returns 3,745 tickers today vs. 3,788 at Day 79. `random.Random(42).sample()` is only deterministic against a *fixed list* — when the underlying sorted ticker list itself shrinks or reorders (SimFin's own coverage changed over ~4 months), the same seed draws a genuinely different sample, not the same one. Caught by chasing down a surprising baseline number before trusting a comparison built on top of it (same discipline as Golden Rule 26/37), rather than assuming a change I made must be the cause just because the number moved after I touched the file. **How to apply:** any time a fixed-seed sample is re-drawn from a data source that itself updates over time (a ticker universe, a coverage list, a live API's current contents), treat "same seed" as necessary but not sufficient for reproducibility — check whether the *input list* is still the same length/order before trusting a before/after comparison, especially across a gap of weeks or months. (Day 107, volume/momentum research spike)

56. **WHEN PRE-REGISTERING A DIRECTIONAL PREDICTION ABOUT A *GATED* BACKTEST, REASON THROUGH EVERY TERM IN THE GATE CONDITION — NOT JUST THE FIRST ONE THAT COMES TO MIND.** Before the Day 112 S&R re-baseline, the pre-registered prediction was "trade count will RISE — the bug made `support_distance_pct` exceed 20%, so the `is_viable` gate rejected setups it shouldn't have." Trades *fell* 75 → 41. The prediction reasoned about the `is_viable` term of the Config C gate (`is_viable AND rr_ratio >= 1.2`) and never considered the `rr_ratio` term — which was the dominant effect: the bug set the reward target to the *highest high in 2 years*, inflating R:R past 1.2 on trades that were never real 1.2:1 setups (NE: R:R 128 with the bug, 0.42 corrected). Fixing it correctly *excluded* those. The pre-registration itself was still valuable — it's what made the miss visible and forced an honest root-cause instead of a quiet retrofit of the reasoning. But a directional prediction is only as good as its coverage of the mechanism. **How to apply:** when writing a pre-registered prediction about how a change moves a gated/filtered result, write out the *full* gate/filter condition first, then reason about the change's effect on *each* term separately — the one you think of first is often not the one that moves the number. Same discipline as Golden Rule 48 ("check whether the statistic you're judging by is even sensitive to the gap"), applied to prediction instead of triage. (Day 112, S&R `_pivot_sr` fix re-baseline — prediction wrong in direction, logged not buried)

60. **A BACKTEST OR FORWARD-TEST RESULT MUST BE PRICED AT A FILL A PERSON COULD ACTUALLY GET. CHECK WHERE THE SIMULATOR ENTERS, NOT WHERE THE LEDGER SAYS IT ENTERED.** MR's forward test was quoted as PF 2.00 for weeks. The ledger recorded each entry at the open, but `daily_job.py` re-scored every trade through `simulate_mr_trade()`, which enters at the entry day's CLOSE (`mr_simulator.py:69`): a price nobody acting on the signal could get. Re-run on the same trades at the next open (`backtest/mr_open_entry_retest.py`), broad MR is **PF 1.50, 63.5% wins, +0.70%/trade**, and HUB-65 is PF 1.07 (break-even). It was caught by a Fable plan review only when the Analyze page was about to tell the user "buy at the open" next to a number earned at the close. **How to apply:** before quoting any system's result, open the simulator and find the line that sets the entry price. Confirm it is a price available after the signal (usually the next open), and that the shown plan uses the same entry. Re-run on the honest basis before quoting, and pre-register the expected change (Golden Rule 56). (Day 123, MR Read card)
