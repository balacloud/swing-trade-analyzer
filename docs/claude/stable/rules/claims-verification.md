# Golden Rules: claims-verification

> Rule text moved word for word from the old GOLDEN_RULES.md (Day 133 layering). Index: `docs/claude/stable/GOLDEN_RULES.md`.

26. **DON'T ACCEPT AN EXTERNAL AUDIT'S DIAGNOSED ROOT CAUSE WITHOUT REPRODUCING IT DIRECTLY — A PLAUSIBLE GUESS CAN BE WRONG IN A WAY THAT MAKES THE SUGGESTED FIX A NO-OP.** A hub-side audit (Session 28, `HANDOFF_sta_audit_session28.md`) found the Context tab's CPI card showing stale-looking values (3.7%/2.8% vs. the real 3.5%/2.6% BLS release) and guessed the cause was cache staleness, suggesting a shorter TTL. A direct live check told a different story: hitting `/api/econ` fresh (`from_cache: false`) reproduced the exact same "wrong" number — proving the cache TTL (already 6h) was never the problem. Tracing the raw FRED response found the real cause: FRED had withheld one month's observation (`2025-10-01: "."`), and `_yoy()`'s fixed-list-index lookback (`series[periods]`) silently shifted onto the wrong calendar month once that gap was filtered out — a date-alignment bug with nothing to do with caching. Shortening the TTL (the audit's suggested fix) would have changed nothing. Before implementing a suggested fix — from an audit, a teammate, or your own first guess — reproduce the symptom yourself against live/fresh data and confirm the named cause actually explains it; only then is the fix guaranteed to do something. (Day 91, Context tab CPI/PMI fix)

37. **WHEN A CITED SOURCE DOESN'T EXIST WHERE POINTED, RESEARCH THE UNDERLYING CLAIM DIRECTLY — DON'T FALL BACK TO A SECONDHAND SUMMARY OF IT.** Asked to read a specific file (`trading-intelligence-hub/research/ibkr_auto_execution_research.md`) documenting a regulatory restriction on automated IBKR order execution, the file didn't exist on disk or in git history — it was very likely only ever a pasted conversation snippet, never saved. A secondhand summary of its conclusion *did* exist, in a sibling project's session-history doc (a prior AI session's paraphrase of the original research). The discipline here wasn't "give up" or "just trust the paraphrase" — it was to research the actual regulation (CIRO Dealer Member Rule 3200) directly against CIRO's own published guidance via web search, which produced a materially more precise and directly-sourced understanding (the exact scope: Order-Execution-Only dealer relationships, real orders to a real marketplace) than the secondhand summary alone would have supported confidently. Same family as Golden Rule 26 (don't accept an external audit's diagnosed root cause without reproducing it directly) — a claim's *existence* in some prior context doesn't substitute for checking the claim itself when it's safety- or compliance-critical and the primary source is available to check. (Day 97, IBKR paper-execution research)

42. **PARALLEL TOOL-CALL RESULTS ARE NOT GUARANTEED TO COME BACK IN CALL ORDER — VERIFY EACH RESULT'S IDENTITY AGAINST A TRUSTED REFERENCE BEFORE TRUSTING IT POSITIONALLY.** While re-sourcing the `/watchlist-report` skill's OHLCV data from IBKR MCP tools instead of yfinance (Day 104), 24 `get_price_history` calls were issued in one batch, one per ticker's known `contract_id`. Two adjacent results came back transposed relative to their tool_use order — confirmed directly, not assumed, by cross-matching each result's own last-close value and daily-volume figure against the pasted watchlist's real numbers (both distinctive enough per ticker to disambiguate). Had the results been trusted positionally, two tickers' entire 3-month OHLCV series — and every indicator computed from them — would have been silently swapped in a live report, with no error, no crash, and numbers plausible enough not to self-flag (both tickers were real ETFs with real, similar-shaped price data). This is a sharper version of Golden Rule 6 ("never claim a result you haven't run") — running the call isn't enough if the *result* isn't verified to belong to the *request* you think it does. **How to apply:** whenever a batch of parallel tool calls returns data that will be labeled/keyed by which call produced it (ticker symbols, file IDs, contract IDs, etc.), do not assume result order equals call order — cross-check each result against an independent, already-trusted identifier (a known price, a known volume, a checksum, an ID echoed back in the response) before using it. If no such identifier is available, fall back to smaller batches or strictly sequential calls where correctness matters. (Day 104, watchlist-report IBKR re-sourcing)

47. **A RULE CITED AS "FIXED" MAY ONLY BE FIXED AT THE SYMPTOM, NOT THE ROOT — CHECK THE LITERAL FUNCTION IT'S NAMED AFTER.** Golden Rule 30 (Day 92) was supposed to fix `fetchSectorRotation()`'s whitelist-reconstruction bug — a fetch function that silently drops any backend field it doesn't explicitly list. But the Day 107/108 full-system audit found the rule had only ever been "fixed" by extending the whitelist each time a dropped field caused a visible problem (Day 67: `size_rotation`/`size_signal`; Day 92 itself: `macro_alignment`) — the actual function the rule is named after was still a manual reconstruction, still capable of silently dropping the next field nobody's looking for yet (live-proven: it was silently dropping a `cached` field nobody had noticed). Every *sibling* function built after Day 92 correctly switched to a genuine pass-through and cited GR30 in a comment explaining why — but the original offender itself was never migrated. This is a distinct failure mode from a rule simply not being applied at all: the citation exists, the fix history exists, everyone reasonably believed it was handled — and it wasn't, at the one place that mattered most. **How to apply:** when an audit or a fresh look revisits a Golden Rule with "this was already fixed" prior art, don't just confirm the rule *exists* and has a fix history — trace the fix to the *exact* file/function the rule is named after and confirm it was actually migrated, not just patched around. A rule with citations elsewhere and silence at its own origin point is not fixed. (Day 108, full-system audit, Group 6a)

48. **BEFORE ESCALATING A SCARY-SOUNDING GAP, CHECK WHETHER THE STATISTIC YOU'RE JUDGING IT BY IS EVEN SENSITIVE TO IT.** The Day 108 full-system audit found Section 8 of `PAPER_TRADING_PREREGISTRATION.md` — VIX-based position-size scaling — was never wired into the automated paper-trading engine at all, for any of the 4 live tracks, since inception. On its face this sounds like a live-vs-frozen-spec divergence serious enough to question the tracks' validity. But `compute_metrics()` — the function computing every number the tracks are actually judged on (win rate, profit factor, expectancy) — operates purely on `return_pct`/`return_r` (percentage return and R-multiple), both **position-size-invariant**: the same trade at any position size produces the identical % return and R-multiple. Position sizing only matters for real dollar risk management, which doesn't exist yet (no capital is deployed). Verified this directly (traced `compute_metrics()`'s inputs, confirmed the ledger schema has no share-count field at all) before reporting the finding's severity — the gap is real and needs fixing eventually, but it currently corrupts nothing. **How to apply:** when a finding sounds alarming because of *what* is missing (a documented safety/scaling rule, a validation step), check *which* statistics that gap could actually influence before setting its urgency — a real gap in an unused code path can be lower-priority than a smaller gap in something the current numbers actually depend on. Don't let the scariness of a missing safeguard substitute for checking whether it's load-bearing yet. (Day 108, full-system audit, Group 3 — also independently applied by the user to the same finding: "VIX is fine, my judgement call")

53. **A LABEL LIKE "NEAREST" IS A CLAIM ABOUT THE CODE, NOT A DESCRIPTION OF IT — VERIFY THE SELECTION LOGIC, NOT JUST THE NAME.** `support_resistance.py`'s `_pivot_sr()` sorts highs/lows ascending, then slices `highs[-cfg.pivot_max_levels:]` / `lows[:cfg.pivot_max_levels]` (`:1048-1050`) — keeping the most EXTREME levels in the lookback window, not the ones closest to price. Every downstream consumer — `assess_trade_viability()`'s support-distance bucketing, both entry panels' displayed R:R, the stop-loss suggestion — calls the result "nearest support" and treats it as literally that. Nothing about this looks broken: no error, no crash, no obviously-wrong number in isolation — the function runs, returns a real price, and the name matches what a reader expects it to mean. That's exactly why it survived undetected as a real, live, open Medium-severity bug (`KNOWN_ISSUES_DAY110.md`) through multiple prior review passes — a name that overstates a computation is a quieter failure mode than a name that's simply wrong, and it doesn't announce itself the way a crash or a null does. **How to apply:** when a variable, function, or field name makes a precise relational claim ("nearest," "closest," "most recent," "primary"), read the actual selection logic before trusting the name — especially before deciding a downstream consumer of that value is "just arithmetic" and therefore safe to leave untouched. The Analyze Page Redesign's item 8 did exactly this, treating S&R's output as clean "Engine" math because the R:R interpretation built on top of it (item 7) was the only piece flagged as unreliable — the unreliability actually starts one layer deeper, in what "nearest" means. (Day 111, five-card technical audit of S&R / MTF Confluence / Price Structure / Pattern Detection / Breakout Status)
